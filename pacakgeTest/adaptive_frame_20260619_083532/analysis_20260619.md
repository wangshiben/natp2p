# 动态自适应帧大小测速日志分析（2026-06-19 用户提供的一次 wifi 跑）

> 本文分析用户单独贴出的一次 `pacakgeTest/relayServer.go` 跑（server1=relay 公网，
> callee/client 为两台 wifi 笔记本）。该跑**数据完整性没问题，但链路基本卡死**，
> 且暴露了帧自适应器一个零吞吐误判 bug。已据此修复 `network/FrameSizeAdaptor.go`。

## 结论速览

- **数据没坏**：trace `duplicate_rx=0 / parse_failures=0 / missing_est=0`，跨中继 1-hop 重写正确。
- **链路是卡死状态**：100 秒内每个 sender worker 只完成约 4 次往返，平均吞吐 ≈ 18 KB/s，
  实时监控绝大多数时间是 `0 B/s`。"0 dup / ✅ 已同步"是因为总共没几个包过去、样本太小才显得干净。
- **自适应器逻辑 bug**：吞吐近零时反而把帧越调越大（已修复）。

## 破绽 1：吞吐塌了 —— 最关键的信号

接收端 trace 分解显示 32 个 worker **每个只收到 4 个包**（个别 5 个）：

```
worker=0 unique=4 max_seq=4 missing_est=0
...
worker=31 unique=4 max_seq=4 missing_est=0
```

sender 是**同步发送**（发一个 → 阻塞等 ACK → 再发下一个）。32 worker × 4 包 ≈ 128 ≈ 总包数 127/129。
也就是 100 秒里每个 worker 只完成约 4 次"发送+收 ACK"往返 → **平均每往返约 25 秒**。

实时监控印证：几乎整段 `⬆️ 0 B/s (0 pkts) | ⬇️ 0 B/s (0 pkts)`，只有零星几秒蹦到 270/313 KB/s。
总量 1.77/1.79 MB ÷ 100s ≈ **18 KB/s**，与健康跑（持续流动、6.5MB）完全不是一回事。

~25 秒/往返 正好对应 `initialAckTimeout=600ms × 指数退避 × maxRetransmitAttempts=6`
（≈ 0.6+1.2+2.4+4.8+9.6+19.2 ≈ 38s 上限）—— 绝大多数包是被重传多次后才勉强过去的。

## 破绽 2：帧大小变更协议在两端打架

callee 侧日志，同一个 `newSize=864` 既确认又超时又再确认：

```
09:27:01 收到帧大小变更确认: newSize=864 confirmed=true   ✅ 已同步 800->864
09:27:03 帧大小变更确认超时: newSize=864                    ❌ 被拒绝或超时，保持 800
09:27:10 收到帧大小变更确认: newSize=864 confirmed=true     （迟到确认又来一个）
```

原因：client 和 callee **两端都在跑 FrameSizeAdaptor、都在发变更请求**，relay 把变更帧当普通
数据来回转发。在破绽 1 那种反复重传的链路上，变更帧本身也经常迟到 → 确认/超时互相错配、状态来回抖。

## 破绽 3：自适应器在"零吞吐"时反而增大帧（已修复 ✅）

日志多次出现：

```
吞吐稳定, 请求 增大 帧:  800 -> 864  (当前: 0 KB/s, 上次: 0 KB/s)
```

**根因**（`network/FrameSizeAdaptor.go` 旧 `tryAdjustByThroughput`）：增大条件是
`currentThroughput >= lastThroughput*0.95`。当吞吐 ≈ 0 时，两个近零值让该式**平凡成立** →
判定为"稳定"→ 增大帧。链路明明卡死，它却理解成"很稳，可加大帧"，方向完全反了。

函数顶部 `if lastThroughput == 0 return` 的保护**形同虚设**：实测吞吐是个很小的浮点数
（如 0.5 KB/s），`int()` 打印成 "0" 但 `!= 0`，绕过了保护。这就是帧一路 800→864→933
上涨、看着像"自适应成功"实为误判的原因。

### 修复

引入绝对吞吐下限 `minHealthyThroughput = 10.0 KB/s`，并在 `tryAdjustByThroughput` 最前面加闸门：

- `currentThroughput < minHealthyThroughput` → **绝不增大**；若当前帧已比最小帧大，则缩小一档，
  否则保持不动，等链路恢复。
- 否则才进入原有的"达到预期95%增大 / 低于85%缩小"逻辑。

新增单测 `network/FrameSizeAdaptor_test.go`（`-race` 通过）：

- `TestAdaptor_ZeroThroughputNeverEnlarges` —— 近零吞吐（绕过 `==0` 保护的 0.x 浮点）绝不增大。
- `TestAdaptor_LowThroughputShrinksFromLargerFrame` —— 已涨到 1200 时吞吐塌了应缩小而非增大。
- `TestAdaptor_HealthyThroughputStillEnlarges` —— 回归：健康吞吐下原"增大"逻辑仍正常。

## 破绽 4：dual KCP+TCP 双 leg 放大了脆弱性

relay 日志每条逻辑连接都出现两次"新连接" + `forward=true`/`forward=false` 配对 + "附加 relay leg"：

```
AcceptTcpStream ... remote=...:22525  (KCP leg，日志标"非TCP连接")
新连接 local=10.6.0.16:9000 ...        (TCP leg)
附加 relay leg 到已有 StreamGroup
```

`pacakgeTest/relayServer.go` 用的是 `TryRegisterRelayStream` + `ConnectNodeWithTargetRelay` 的
**双 leg** 路径。而跨中继场景我们之前专门把 natnode 换成 **TCP 单 leg**
（`TryRegisterRelayStreamTCP`），就是因为双 leg 在真实公网/wifi 下某条 leg 中途 EOF 会让转发时好时坏。
这次两端是 wifi 笔记本（网卡 `wlp3s0` / `WLAN`），双 leg 脆弱性被放大，是反复重传的重要诱因。
日志末尾 `TCP leg 失败, 关闭(relay 端不重连): err=EOF` 即 leg 掉线现象。

## 一个"非破绽"：Tx/Rx 包数对不上是统计假象

client 报"上传 100 包"，callee 报"下载 129 包"——收到比发出还多，看着吓人，但这是
`TrafficMonitor` 自己的口径：Total 计数只在每秒 tick 时累加，**结束前不足 1 秒的窗口会漏掉**
（`relayServer.go` 注释 155-163 行自述），且 Tx 只在收到 ACK 后才 +1。
可信的是 trace 的 `duplicate_rx=0 / missing_est=0` —— **数据完整性没问题，只是吞吐和计数难看**。

## 后续建议

1. **[已修复]** 自适应器零吞吐误判：低于绝对下限禁止增大。
2. ~~测速程序切到 TCP 单 leg~~ —— **用户决定不切单 leg**，保留 dual KCP+TCP。双 leg 的
   failover 抖动改由「破绽 2 收敛 + 破绽 1 健康闸门」缓解，不动 leg 拓扑。
3. **[已规划，见下]** 帧变更**只让一端发起**，避免两端同时发请求互相错配。实现计划见下一节。

# 帧变更单端发起：实现计划

> 目标：消除破绽 2（两端同时跑 FrameSizeAdaptor、都发变更请求，在高重传链路上确认/超时互相错配）。
> 原则：**单一决策者**——一端为 initiator（测吞吐、决定帧大小、发起变更），另一端为 follower
> （只接收请求、应用 `SetFrameSize`、回 ACK，自己绝不发起）。协议帧格式与握手流程**完全不变**，
> 只改「谁有资格发请求」。

## 现状（为何两端会打架）

- `networkFrameWork/TcpStream.go:116` 每个流都无条件 `NewKCPFrameSizeAdaptor()`；
- `:142` 每个流都无条件 `adaptor.SetFrameSizeChangeCallback(t.requestFrameSizeChange)`；
- `:541` `writeFrames` 对所有流（含 pureForwarder relay leg）都 `RecordBytesSent`；
- 结果：client 与 callee 两端都在测吞吐、都在发 `FrameTypeFrameSizeChange(SeqId=0)` 请求，
  在反复重传的链路上两个方向的请求/确认交错 → 同一个 `newSize` 既确认又超时又迟到确认。

## 设计

### 1. 角色定义

| 角色 | 行为 |
|------|------|
| **initiator** | 跑吞吐统计 → `tryAdjustByThroughput` → 满足条件时发 `FrameTypeFrameSizeChange(SeqId=0)` 请求，等对端 ACK 后应用 |
| **follower** | **绝不发起**；收到请求 → 校验区间 → `SetFrameSize` 应用 → 回 ACK(SeqId=1)。自身帧大小完全跟随 initiator |

帧大小成为**单写者**：仅 initiator 写决策，follower 镜像。两个方向的发送都用同一个帧大小
（follower 收到请求后 `SetFrameSize`，其出站 `GetFrameSize()` 也随之变），保持一致。

### 2. 角色如何指派（核心决策）

**默认采用 dial / accept 不对称**，零应用改动、每条连接恰好一个 initiator：

- **拨号方 = initiator**：`NewTCPStream`（`TcpStream.go:154`，client 主动 `ConnectNode` 的路径）。
- **接受方 = follower**：`AcceptTcpStream` / `AcceptTcpStreamSync`（`:161` / `:180`，callee 侧）。
- **pureForwarder relay leg 恒为 follower**：relay 的桥接 leg 只透传裸帧，绝不参与帧大小决策。
  即使它走的是拨号构造路径，也必须因 `pureForwarder==true` 而被排除在 initiator 之外。

> 为什么用 dial/accept 而非 nodeId 比较：TcpStream 当前只存对端 `nodeId`（`:124`），不存自身 id，
> 做不到对称的 `min(ownId, peerId)` 选举而不额外打通自身 id。dial/accept 这条不对称在
> 点对点流里天然存在、单端唯一，最省改动。若将来出现「无明确拨号方」的场景，再补 nodeId 选举。

### 3. 代码改动清单

1. **`networkFrameWork/TcpStream.go`**
   - 结构体 `TcpStream` 加字段 `frameSizeInitiator atomic.Bool`（默认 false）。
   - 新增导出方法 `SetFrameSizeInitiator(bool)`：置位，并据此**安装/卸载**回调——
     `true` 时 `adaptor.SetFrameSizeChangeCallback(t.requestFrameSizeChange)`，
     `false` 时 `adaptor.SetFrameSizeChangeCallback(nil)`。
   - `newTcpStream`（`:111`）**移除**无条件安装回调那行（`:142`），改为默认 follower（回调 nil）。
   - `NewTCPStream`（`:154`，拨号入口）构造后调用 `t.SetFrameSizeInitiator(true)`。
   - Accept 路径（`AcceptTcpStream` / `AcceptTcpStreamSync`）保持默认 follower，不调用。
   - relay 桥接侧在 `SetPureForwarder(true)`（`:594` 附近）时强制 `SetFrameSizeInitiator(false)`，
     防止「拨号构造的 relay leg」误带 initiator。
   - `requestFrameSizeChange`（`:974`）入口加一道断言/早退：`if !t.frameSizeInitiator.Load() { return false }`，
     双保险（即便回调被误装也不会发请求）。

2. **`network/FrameSizeAdaptor.go`**
   - `tryAdjustByThroughput`（`:147`）现有 `if a.onFrameSizeChange != nil` 已天然把 follower 挡在
     「发起」之外（follower 回调为 nil → 永不设 `pendingFrameSize`、永不发请求）。**无需改动决策逻辑**。
   - 可选优化：follower 端 `RecordBytesSent` 仍在累计吞吐但无用，可在 TcpStream 侧据
     `frameSizeInitiator` 跳过 `RecordBytesSent`（`:540`）省 CPU；非必需，先不做以缩小改动面。

3. **协议帧 / handler 不动**
   - `handleFrameSizeChangeRequest`（`:1014`，应用+ACK）、`handleFrameSizeChangeAck`（`:1040`）、
     `sendFrameSizeChangeAck`（`:1056`）、`FrameTypeFrameSizeChange` 分发（`:685`）全部保持原样。

### 4. 边界与权衡（需在 review 时确认）

- **链路不对称**：帧大小只由 initiator 方向（client→callee）的吞吐驱动，反向沿用同值。
  对大致对称的链路无碍；强不对称链路下反向不是最优，但换来「单一真相、无抖动」，可接受。
- **误配双 follower**：两端都不发起 → 帧大小停在 800 默认值（安全）。比双 initiator 打架好。
- **向后兼容**：
  - 新 follower × 旧（双发起）对端：旧端发请求、新 follower 应用+ACK —— 兼容。
  - 新 initiator × 旧对端：新端发起，旧端既应用又**仍会自己发起** —— 仍可能抖动。
    **完整收益需两端都升级**。此点须在发布说明里写清。

### 5. 验证计划

- **单测**（`networkFrameWork/TcpStream_test.go` 或新文件）：
  - follower 端 `tryAdjustByThroughput` 在健康吞吐下**不产生** `FrameTypeFrameSizeChange(SeqId=0)`
    写出（用假 conn 断言无该类型帧）。
  - follower 收到请求后 `GetFrameSize()` 等于请求值，并回了 ACK(SeqId=1)。
  - initiator 端健康吞吐下正常发起并在收到 ACK 后应用（沿用现有自适应单测路径）。
- **三服务器复测**（同需求 2 拓扑）：观察 callee 日志中**不再出现** `请求 增大/减小 帧` 与
  `帧大小变更确认超时` 的来回错配；只 client 侧出现发起、callee 侧只出现「✅ 已应用对端请求的帧大小」。

### 6. 落地顺序

1. 加字段 + `SetFrameSizeInitiator` + 改 `newTcpStream`/`NewTCPStream`/`SetPureForwarder`。
2. `requestFrameSizeChange` 入口早退做双保险。
3. 补单测，`go test ./networkFrameWork/ -race`。
4. 三服务器复测，确认 callee 侧无错配日志。
5. 提交，发布说明注明「完整收益需两端同时升级」。

> **注：下一节的 MaxMutx 协商方案取代了本节「dial=initiator 默认」的角色指派规则。**
> 本节的 initiator/follower 机制（单写者、回调装卸、pureForwarder 排除）仍然成立，
> 只是「谁是 initiator」改由 MaxMutx 大小决定（小帧方掌权），dial/accept 仅作相等时的 tiebreak。

# MaxMutx 协商 + 帧调控权归属：实现计划（待 review，未落地）

> 对应用户新增需求：
> 1. 加密连接建立后的**第一帧**交换 MaxMutx（本端网卡可接受的最大帧）；**阻塞式**——必须收到
>    对端 MaxMutx 后才正式开始数据传输；以 `min(local, peer)` 作为帧大小**上限**。
> 2. **帧小（MaxMutx 小）的一方**掌握调整帧大小的权利。
> 3. MaxMutx **相等**时，由**连接发起方**（拨号方）调控。
>
> 本方案与上一节「单端发起」整合：**掌权方 = initiator**（跑自适应、发变更请求），
> **另一方 = follower**（只应用+ACK，绝不发起）。

## 关键约束（来自代码勘察，决定了方案形状）

- **首帧已被占用，不能动**：拨号方连上后的第一帧是 pubkey 首消息（`Dialers.go:252`
  `SendMessage(FirstMessage)`）。relay 靠它路由、`sha256(payload)` 推 nodeId、并决定是否走裸字节
  桥接（`TransportCoverStream.go` / `readFirstMessageSync` `TcpStream.go:214`）。把 MaxMutx 塞到它
  之前要重写 relay 路由握手，面太大、风险高——**不做**。
- **加密握手在 pubkey 首消息之后完成**：`NewTLSCrypto(stream, keyPair)` 走 ECDH/TLS over stream，
  完成点：
  - 拨号方：`networkFrameWork/client/ClientStream.go:204-209`（`NewTLSCrypto` + `SetCryptoSuite`）。
  - 接受方：`p2pnode/impl/natnode/handshake_impl.go:32-36`（`HandshakeIncoming`）。
  - natnode 出站：`handshake_impl.go:47-51`（`HandshakeOutgoing`）。
  - **「加密连接建立后的第一帧」= `SetCryptoSuite` 之后发出的第一帧**，MaxMutx 锚在此处。
- **relay 转发腿天然被排除**：pure forwarder 腿从不调 `NewTLSCrypto`，故把 MaxMutx 挂在 crypto
  完成点 = 只有真正的 app 端点（client / callee）参与，转发腿不掺和。无需额外判断。
- **readLoop 此时已在跑**：拨号侧 `startTcpStream` 构造即启 readLoop（`TcpStream.go:150`），
  所以**不能裸同步读** advert，必须走 `handleFrame` + channel 信号（复用现有
  `frameSizeChangeAcks` 那套模式）。
- **localMax 已算好，无需重测**：`newTcpStream` 构造时已 `DetectMaxFrameSize(conn)` 并
  `SetMaxFrameSize`（`TcpStream.go:119-122`），值存进 adaptor.maxFrameSize。交换时直接读它当
  localMax，收到 peerMax 后再 `SetMaxFrameSize(min(local,peer))` 二次钳制。

## 编码：新增控制帧 `FrameTypeMaxFrameAdvert`

- `network/Frame.go`：`FrameTypeMaxFrameAdvert uint8 = 4`。值放 **AckId**，空 payload（就是个 MTU
  数字、不敏感，明文即可）。与现有 `FrameTypeFrameSizeChange=3` 完全同模式——不动数据帧线格式，
  `FrameHeaderLength` 不变，relay `io.Copy` 透传不受影响。
- **兼容性硬约束（重要）**：旧节点 `handleFrame` 的 `default` 分支对未知帧类型
  `return errors.New("unknown frame type")` → 触发 `failAndClose` **直接断连**（`TcpStream.go:693`）。
  故新旧节点**不可混用**，必须两端同时升级。发布说明必须显著标注。

## 交换协议（阻塞、互发、互为确认）

1. crypto 建立后（`SetCryptoSuite` 之后），app 层各端调用 `stream.ExchangeMaxFrame(localMax)`。
2. `ExchangeMaxFrame`：发 `FrameTypeMaxFrameAdvert(AckId=localMax)` → **阻塞**在 channel 等
   `handleFrame` 投递对端 advert（超时见下）。返回前**不发任何业务数据**。
3. `handleFrame` 收到 `FrameTypeMaxFrameAdvert` → 记录 peerMax、signal channel。
4. **互发即互为确认**：两端各自收到对端 advert 才返回。对端 advert 既携带它的值、又证明它已跑到
   交换这一步（即它也不会在 advert 前发数据）→ 无需独立 ACK，天然绕开 pureForwarder 不回 ACK 的坑。
5. 返回后：`cap = min(localMax, peerMax)` → `SetMaxFrameSize(cap)` → 定角色（见下）→ 才允许发数据。

> **为何不会读到对端提前发来的数据**：双方都遵守「advert 前不发业务数据」，readLoop 在 advert
> 到达前只会收到对端 advert（控制帧，不入 inbox）。

## 帧调控权归属（需求 2 + 3）

各端在 `ExchangeMaxFrame` 后已知 `localMax`、`peerMax`、`iAmDialer`（dial=true / accept=false）。纯函数：

```
governing = (localMax < peerMax) || (localMax == peerMax && iAmDialer)
```

- `governing==true` → `SetFrameSizeInitiator(true)`：装 `onFrameSizeChange` 回调、跑自适应、发
  `FrameTypeFrameSizeChange`。
- `governing==false` → follower：只在收到请求时 `SetFrameSize`+ACK，绝不发起。
- 两端依据**相同**的 `(localMax, peerMax, 谁拨号)` 必得**互斥且一致**的结论（一个 true 一个 false）。

## 边界与风险

- **兼容性（硬失败）**：旧节点收到未知帧类型直接断连。新旧不可混，须两端同时升级。
- **超时/对端无 advert → 重试 ≤3 次后断连**（已定）：`ExchangeMaxFrame` 每次等待超时（如单次
  `advertTimeout=2s`）即**重发 advert** 并重等，最多重试 **3 次**；3 次重试后仍未收到对端 advert →
  `failAndClose` **直接断连**，不降级、不放行数据。理由：拿不到对端 MaxMutx 就无法确定帧上限与
  调控权归属，带着错误上限继续打流比断连更糟。
- **dual leg（KCP+TCP）MTU 不一致 → 加密握手成功后补发一帧确认**（已定）：两腿网卡 MTU 可能不同。
  做法——`SetCryptoSuite` 成功后，在 DualStream 上跑**这次 MaxMutx advert 交换**本身即作为「确认帧」：
  本端取两腿 `DetectMaxFrameSize` 的**较小值**作为 localMax 写入 advert，对端回 advert 后双方落到
  `min(local,peer)`。即「补发的那一帧」= advert 帧，承载已 reconcile 的单一值，无需为选主腿做额外猜测。
- **跨中继 per-hop MTU**：MaxMutx 是**端到端 app 帧大小**协商；真实 per-hop MTU 由 TCP MSS/PMTUD
  处理，二者不冲突。
- **natnode 进程内测试偏 flaky**（KCP 调度，见 [[natnode-inprocess-tests-flaky]]）→ 以真实服务器实测为准。
- **cap 下限**：`SetMaxFrameSize` 会把 `<minFrameSize(800)` 拉回 800；`min(local,peer)` 落在 800 以下
  时即固定 800，符合预期。
