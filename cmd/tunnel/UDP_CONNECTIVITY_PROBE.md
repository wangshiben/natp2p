# UDP/KCP 跨服务器连通性探测报告

**探测时间**: 2026-06-27
**起因**: 部署验证发现跨中继 KCP 用不上, 需查清 UDP 到底为何不通
**结论**: ✅ **TCP 全通, UDP 全部被阻断 —— 阻断点在云安全组层面(非系统/非线路), 放行 UDP 入站后 KCP 即可用**

---

## 1. 探测方法

用与生产代码同库(xtaci/kcp-go v5)的最小探测工具 `kcpprobe`, 以及 python raw UDP socket,
对三台服务器做交叉连通性测试:
- 38(香港)
- 104(美国)
- 129(成都, 腾讯云)

测试维度: KCP 握手/ping、raw UDP 单向丢包、TCP 对照、本机回环对照、本地 iptables 检查。

---

## 2. 探测结果

### 2.1 KCP ping(echo 回显)
| 链路 | KCP 拨号 | ping 回显 |
|------|----------|-----------|
| 129 → 38 | "成功"(UDP无连接,假成功) | ❌ timeout |
| 104 → 38 | "成功" | ❌ timeout |
| 38 → 129 | "成功" | ❌ timeout |
| 38 → 104 | "成功" | ❌ timeout |

注: KCP 基于 UDP 无连接, DialWithOptions 不握手, "拨号成功"不代表通; ping 回显才是真连通判据。

### 2.2 raw UDP 单向丢包(绕过 KCP 协议层)
| 链路 | 发包 | 收包 |
|------|------|------|
| 129 → 38:19999 | 发 10 包 | ❌ 38 raw socket 零接收 |
| 38 → 129:19999 | 发 10 包 | ❌ 129 raw socket 零接收 |

**UDP 包在到达对端系统前就全部丢失。**

### 2.3 TCP 对照(同端口/同机器)
| 链路 | TCP:9000 |
|------|----------|
| 129 → 38 | ✅ 可达 |
| 104 → 38 | ✅ 可达 |
| 本地 → 38 | ✅ 可达 |

(之前测"129→38:9000 不可达"是因 38 当时无服务监听=connection refused, 启 python 监听后全部可达。)

### 2.4 排除性对照
- **38 本机回环 UDP**: ✅ 正常(127.0.0.1 自发自收成功)→ 系统 UDP 功能无问题
- **38 本地 iptables**: 空规则、默认 ACCEPT → 本地防火墙没挡 UDP

---

## 3. 结论与定位

### 3.1 阻断点
| 候选 | 排除依据 | 判定 |
|------|---------|------|
| 系统 UDP 功能 | 本机回环 UDP 正常 | ✅ 排除 |
| 本地 iptables | 规则为空、默认 ACCEPT | ✅ 排除 |
| 大陆墙(GFW) | 104(美国)↔38、129(国内)↔38 全不通,海外也不通 | ✅ 排除(非定向墙) |
| **云安全组(网络 ACL)** | TCP 放行而 UDP 默认拒绝, 包在到达系统前被丢 | ⭐ **判定为此** |

### 3.2 核心结论
**这些云服务器的 UDP 入站被安全组默认拦截, 不是网络线路或 GFW 的问题。**
腾讯云等公有云默认安全组通常只放行少量 TCP 端口(22/80/443等), UDP 需手动放行。

### 3.3 对 KCP/路线 B 的意义
- ✅ **好消息**: UDP 不通是可修复的配置问题, 不是物理限制
- **放行各 relay 的 KCP UDP 端口(9000/9001)后**, KCP 即可工作:
  - relay 间(38↔104↔129)桥接可走 KCP, 在跨境/高 RTT 段发挥拥塞控制优势
  - 路线 B 的 dual + KCP 优先建桥才能真正生效

## 4. 待用户确认 / 下一步

### 4.1 需要你操作的
**在三台服务器的云控制台安全组放行 UDP 端口**(KCP 用):
- 38: 放行 UDP 9000
- 104: 放行 UDP 9001
- 129: 放行 UDP 9000(若作 relay)
- (家宽客户端→relay 这跳: 客户端是出站, 一般不受限; 但若 relay UDP 入站放行, 客户端 KCP 应能连上)

### 4.2 放行后重新验证
1. 重跑 `kcpprobe` 确认 UDP 连通 + KCP ping/吞吐
2. 重跑跨中继隧道, 确认桥接选 KCP(而非 TCP 兜底)
3. 测 20MB 带宽, 对比 TCP 基线

### 4.3 仍需的代码改动(独立于安全组)
即使放行 UDP, **桥接 peerConn(`dialRawBridgeConn`)仍写死 TCP**,
relay 间转发不会自动用 KCP。要让 relay 间走 KCP, 仍需改 `dialRawBridgeConn` 支持 KCP 拨号。
