## 3. 部署过程与遇到的问题

### 3.1 问题一：104 无法访问 129 的 Index 端口（云安全组阻断）

**现象**:
按原计划用 `129.0.0.2:9000` 作为 index，但 104 机器无法连接：

```
104 → 129:9000   ❌ 不可达
104 → 129:8911   ❌ 不可达
104 → 38.0.0.2:9000   ✅ 可达
104 → 103.0.0.1:9000    ✅ 可达
```

**排查过程**:

| 检查项 | 结果 |
|--------|------|
| 104 IPv4 出口 | ✅ 104.0.0.2 正常 |
| 104 → 129 路由 | ✅ `via 104.0.0.3 dev eth0` 正常 |
| 104 ping 129 | ❌ 100% 丢包 |
| 129 上 9000 监听 | ✅ `indexServer` 监听 `*:9000` |
| 129 本机连 9000 | ✅ 可达 |
| 129 iptables | ✅ INPUT policy ACCEPT，无 DROP |
| 129 YJ-FIREWALL 链 | 54 条 REJECT 黑名单，**104 不在其中** |
| 本地（其他 IP）连 129:9000 | ✅ 可达 |

**根因**:
- 129 机器内部 iptables **不阻断** 104
- 129 本机和本地测试机都能连 129:9000
- **唯独 104 连不上** → 阻断发生在**云厂商安全组**（腾讯云控制台层面），9000 端口只放行了部分来源 IP，未放行 104.0.0.2

**结论**: 这是云平台安全组配置问题，需在腾讯云控制台为 9000 端口放行 104 的 IP（或 0.0.0.0/0），无法通过机器命令行解决。

### 3.2 解决方案：用 Relay 直连绕过 Index

NAT 节点 bootstrap 通常需先连 index 发现 relay。但 `tunserver`/`tunclient` 均支持 `-relay` 参数**直接固定到指定 relay，完全跳过 index**：

```go
// server/main.go & client/main.go
bootstrapAddr := *indexAddr
if *relayAddr != "" {
    bootstrapAddr = *relayAddr  // 跳过 index，直连 relay
}
```

104 已验证能连 `38.0.0.2:9000`（这是一台注册在 129 下的真实 relay）。因此：
- Server（104）和 Client（本地）**都固定到 `38.0.0.2:9000`**
- 双方落在同一 relay 上，无需 129 即可建立隧道

## 4. 部署执行

### 4.1 二进制部署

```bash
# 交叉编译 linux/amd64
GOOS=linux GOARCH=amd64 go build -o httpfileserver ./cmd/tunnel/httpfileserver/
GOOS=linux GOARCH=amd64 go build -o tunserver ./cmd/tunnel/server/
# 经 ProxyJump 传输到 104
scp httpfileserver tunserver server-host:/tmp/
```

### 4.2 启动 Server 端（104）

```bash
# HTTP 文件服务器（20MB）
/tmp/httpfileserver -port 5173 -size 20
# → SHA256: ec750930433667c7dd6df3368675b365431a2fb70780659362695fcf4669615f

# Tunnel Server（固定 relay 38.76）
/tmp/tunserver -target 127.0.0.1:5173 -relay 38.0.0.2:9000
# → NodeID: 7569d0788bb94678241ddb8f19a1c40e3a6bd2117a8df544eb9de977549e5a01
```

### 4.3 启动 Client 端（本地）

```bash
/tmp/tuntest/bin/tunclient \
    -target 7569d0788bb94678241ddb8f19a1c40e3a6bd2117a8df544eb9de977549e5a01 \
    -listen 127.0.0.1:8888 \
    -relay 38.0.0.2:9000
# → 已建立隧道连接
```

## 6. 性能瓶颈根因分析

### 6.1 基线对比

| 场景 | RTT | 速度 | 倍率 |
|------|-----|------|------|
| 104 本机直连 HTTP（无隧道） | ~0 | **406 MB/s** | 基准 |
| 本地全套模拟（环回隧道） | ~0 | **30 MB/s** | 1/13 |
| 跨公网经 relay 隧道 | **308ms** | **0.05 MB/s** | **1/8000** |

### 6.2 RTT 测量

```
本地 → 38.0.0.2 : RTT 115ms
104  → 38.0.0.2 : RTT 193ms
链路总 RTT ≈ 115 + 193 = 308ms
```

### 6.3 根因：停等式（Stop-and-Wait）逐帧确认

**计算验证**:
- mux 层 `Write` 分块大小：32 KB（`stream.go: maxChunk = 32 * 1024`）
- 实测吞吐：48 KB/s ÷ 32 KB ≈ **1.5 帧/秒**
- 链路理论帧率：1 / RTT = 1 / 0.308s ≈ **3.2 帧/秒**

实测帧率与 `1/RTT` 同数量级，**证明每发送一个数据帧需要等待约一个完整 RTT 的往返确认**才能发下一帧。吞吐被 RTT 死死限制，与带宽无关。

**瓶颈定位层次**:

| 层 | 是否瓶颈 | 说明 |
|----|---------|------|
| 应用层（curl/http） | ❌ | 104 本机直连 406 MB/s |
| mux 多路复用层 | ❌ | `sendFrame` 仅 `conn.Send`，无 ACK 等待；本地环回 30 MB/s |
| **P2P 连接层（natnode 经 relay 转发）** | ✅ **瓶颈** | 经 relay 的逐帧同步确认，受 RTT 限制 |

底层 `p2pnode.Connection.Send()` 经 relay 转发时采用**同步逐帧确认**机制，没有滑动窗口/流水线（pipelining）。在低 RTT（本地环回）下不明显，但在 308ms 跨公网 RTT 下，吞吐塌缩到 ~3 帧/秒。

### 6.4 为什么本地测试没暴露

本地全套模拟所有进程都在环回网络（RTT≈0），停等协议每帧确认几乎零延迟，所以能跑到 30 MB/s。**只有真实跨公网部署（高 RTT）才会暴露这个停等瓶颈**——这正是本次部署测试的价值。

## 7. 结论

### 7.1 已验证可用的部分 ✅

1. **隧道架构正确**：Client 监听本地端口 → 经 relay → Server 转发到本地服务，链路完全打通
2. **Relay 直连绕过 index 可行**：用 `-relay` 固定双方到同一 relay，无需 index
3. **数据正确性**：小数据（health/checksum）经隧道传输内容准确
4. **跨公网连通**：本地 ↔ 38.76 relay ↔ 104 三方 P2P 连接建立成功

### 7.2 发现的问题 ❌

| 问题 | 严重度 | 性质 | 解决途径 |
|------|--------|------|---------|
| 129:9000 云安全组阻断 104 | 🟡 中 | 配置问题 | 腾讯云控制台放行 9000 端口 |
| 跨公网大文件传输停等瓶颈 | 🔴 高 | 架构缺陷 | 底层 P2P 连接层加滑动窗口/流水线 |

### 7.3 核心结论

**隧道功能正确，但底层 P2P 转发层的停等式逐帧确认机制，使其在高 RTT 跨公网场景下无法承载大文件传输**。20MB 文件按 48KB/s 计算需约 7 分钟，实用性差。

**这与本地测试（30 MB/s）形成鲜明对比**，问题根源不在 tunnel/mux 应用层，而在 natnode 经 relay 转发的连接层。

---

## 8. 改进建议

### 8.1 短期（绕过/缓解）

1. **放行 129 安全组**：腾讯云控制台为 9000 端口放行所有来源，恢复 index 可用性
2. **小流量场景可用**：当前隧道适合 API 调用、控制信令等小数据交互

### 8.2 中期（核心修复，高优先级）

3. **P2P 连接层引入滑动窗口**：允许多个数据帧在途（in-flight）而非逐帧等待 ACK，是解决吞吐瓶颈的关键
   - 目标：窗口大小 ≥ `带宽 × RTT`（BDP），例如 10Mbps × 0.3s ≈ 384KB，需至少 12 个 32KB 帧在途
4. **批量 ACK / 累积确认**：relay 转发层改为累积确认，减少往返次数

### 8.3 长期（架构优化）

5. **NAT 打洞直连**：让两端尝试 UDP 打洞建立直连，绕过 relay 中转，消除 relay 转发开销
6. **拥塞控制**：引入类 BBR/CUBIC 的拥塞窗口动态调整

## 10. 带宽基线测试（分段测量，修正根因）

### 10.1 测试方法

用**同一个 20MB 文件**，分别测量隧道路径上每一跳的**原始 HTTP 带宽**（不经隧道，httpfileserver 监听 0.0.0.0 直连），以确定理论瓶颈：

```
隧道数据流: 104(http) → 38(relay) → 本地(client)
对应分段:   段2(38←104)    段1(本地←38)
```

测试脚本: `cmd/tunnel/localsim/bandwidth_baseline.sh`

### 10.2 带宽矩阵

| 测量段 | 方向 | 原始 HTTP 带宽 | 链路性质 |
|--------|------|---------------|----------|
| **段1** | 本地 ← 38 | **0.045 MB/s** | 跨境（中国→美国），国际出口瓶颈 ★最低 |
| **段2** | 104 ← 38 | **6.84 MB/s** | 美国机房间互联，快 |
| 参照1 | 本地 ← 国内镜像(清华) | 1.8 MB/s | 国内带宽正常 |
| 参照2 | 本地 ← 104 直连 | 不通 | 104 安全组未放行 18080 |

**段1、段2 数据均为完整 20MB 传输、SHA256 校验一致的有效测量。**

### 10.3 链路质量

| 指标 | 本地→38 | 38→104 |
|------|---------|--------|
| RTT 平均 | 151ms（抖动 74~272ms，mdev 65ms） | ~193ms（稳定） |
| 丢包率 | 0% | 0% |

本地→38 **丢包为 0 但 RTT 剧烈抖动**，是跨境国际出口拥塞/QoS 限速的典型特征。

### 10.4 隧道端到端 vs 理论瓶颈

| 项目 | 带宽 | 占瓶颈段(段1)比例 |
|------|------|------------------|
| 理论瓶颈 = min(段1, 段2) = 段1 | 0.045 MB/s | 100% |
| **隧道端到端实测**（60s 平均，2 次） | **0.0134 MB/s** | **~30%** |
| 期望值（题设 90%） | ~0.040 MB/s | 90% |

**隧道实测稳定在 0.0134 MB/s（两次完全一致），仅达到瓶颈段带宽的约 30%。**

### 10.5 修正后的结论（双层瓶颈）

**第一层 — 绝对带宽瓶颈（物理上限，不可优化）**:
- 段1 跨境链路（中→美）原始带宽只有 **~0.045 MB/s**
- 这是 HTTP 直连即存在的物理限制，**任何隧道方案都无法突破**
- 之前报告把 0.05 MB/s 全部归因于隧道停等协议是**误判**——实际上原始链路就这么慢

**第二层 — 隧道效率损耗（可优化部分）**:
- 隧道只发挥了瓶颈带宽的 **~30%**，损失约 70%
- 在已经很低的跨境带宽 + 高 RTT 抖动下，mux/底层连接的**逐帧同步确认**进一步放大了损耗
- 这部分（30% → 接近 90%）是隧道协议层真正可优化的空间

### 10.6 验证题设理论

> 题设："整套流程的网络带宽应在最低带宽的 10% 偏差内（即 ≥90%）"

**实测未达标**：隧道带宽 / 最低段带宽 = 0.0134 / 0.045 ≈ **30%**，远低于 90%。

**差距归因**：这 60% 的额外损耗（90% 期望 − 30% 实测）来自隧道协议层，主要是底层 P2P 连接经 relay 转发的**停等式逐帧确认**——在高 RTT（约 350ms 端到端）下，每帧往返等待严重限制了流水线效率。这印证了 §6 关于停等机制的分析方向是对的，只是它**不是绝对带宽低的主因（跨境链路才是），而是效率打三折的主因**。

### 10.7 优化方向（区分两层）

| 瓶颈层 | 能否优化 | 措施 |
|--------|---------|------|
| 跨境绝对带宽 | ❌ 不可（物理限制） | 换国内 relay / 国内中转，或接受低带宽 |
| 隧道效率 30%→90% | ✅ 可优化 | **底层连接层引入滑动窗口/流水线**（核心）；批量 ACK；NAT 打洞直连绕过 relay |

**优先级最高的优化**：在 P2P 连接层实现滑动窗口（允许多帧在途），目标窗口 ≥ 带宽×RTT。这能把隧道效率从 30% 提升到接近链路上限，使隧道带宽逼近段1的 0.045 MB/s。

### 10.8 复现方法

```bash
# 1. 部署 httpfileserver 到 38 和 104（监听 0.0.0.0）
GOOS=linux GOARCH=amd64 go build -o /tmp/d/httpfileserver ./cmd/tunnel/httpfileserver/
scp /tmp/d/httpfileserver relay-host:/tmp/   # 38
scp /tmp/d/httpfileserver server-host:/tmp/   # 104

# 2. 运行分段带宽基线脚本
bash cmd/tunnel/localsim/bandwidth_baseline.sh

# 3. 隧道端到端对照（手动）
ssh server-host 'nohup /tmp/tunserver -target 127.0.0.1:18080 -relay 38.0.0.2:9000 >/tmp/s.log 2>&1 & sleep 9; grep "本节点 ID" /tmp/s.log'
/tmp/tuntest/bin/tunclient -target <NodeID> -listen 127.0.0.1:8888 -relay 38.0.0.2:9000 &
curl -s -m 65 -o /tmp/t.bin http://127.0.0.1:8888/file & sleep 60; kill %1  # 看 60s 下载量
```
