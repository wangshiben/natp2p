# 跨境链路带宽优化报告（本地 → 38 香港）

**测试时间**: 2026-06-27  
**链路**: 本地（中国大陆）→ 38.0.0.2（香港）  
**测试文件**: 20MB  
**结论**: ✅ 找到根因并验证有效方案，单流带宽提升 **27 倍**（0.062 → 1.672 MB/s）

---

## 1. 问题背景

香港离大陆很近，理论 RTT 应 30-50ms，但实测：
- RTT 抖动 74~272ms（mdev 65ms），丢包 0%
- 单流 HTTP 下载仅 **0.062 MB/s**
- 而 38→104（香港→美国机房）能跑 6.84 MB/s

说明 **38 服务器上行带宽充足，瓶颈在"本地→38"这条特定链路的单连接传输**。

---

## 2. 诊断测试与数据

### 2.1 并发流测试（证明单连接被限制）

| 并发数 | 总带宽 | 相对单流 |
|--------|--------|---------|
| 单流（CUBIC） | 0.062 MB/s | 1x |
| 8 并发 | 0.734 MB/s | **11.7x** |
| 16 并发 | 1.185 MB/s | **19x** |

**结论**: 总带宽远不止 0.062 MB/s，是**单 TCP 连接被压制**。多连接能聚合占用更多带宽 → 大陆国际出口对单流有拥塞/QoS 限制。

### 2.2 拥塞控制算法测试（找到真正根因）

初始状态：本地和 38 都用 **CUBIC**。

| 配置 | 单流带宽 | 提升 |
|------|---------|------|
| CUBIC 单流 | 0.062 MB/s | 基准 |
| **BBR 单流** | **1.333 ~ 1.672 MB/s** | **21~27x** |
| BBR + 4 并发 | **5.333 MB/s** | **86x** |

**完整 20MB 传输（BBR 单流）**: 11.96 秒，1.672 MB/s，SHA256 校验一致 ✅

### 2.3 根因

**大陆→香港链路存在丢包/抖动。CUBIC 把丢包误判为网络拥塞而疯狂降速；BBR 基于"带宽×延迟"建模，不被丢包欺骗，直接逼近链路真实容量。**

这也解释了为什么并发能提速：多个 CUBIC 流各自降速后，聚合起来才接近 BBR 单流的效果。

---

## 3. 优化方案（按收益/成本排序）

### 方案一：服务端启用 BBR ⭐⭐⭐（已实施，最高性价比）

**收益**: 单流 27 倍提升（0.062 → 1.672 MB/s），零成本，立即生效。

**原理**: 下行速度由**发送方**（38 服务器）的拥塞控制决定，所以在 38 上启用 BBR 即可。

**已在 38 实施并持久化**:
```bash
modprobe tcp_bbr
sysctl -w net.core.default_qdisc=fq
sysctl -w net.ipv4.tcp_congestion_control=bbr
# 已写入 /etc/sysctl.conf，重启后仍生效
```

**对隧道的意义**: tunnel server / relay 所在机器都应启用 BBR。数据从哪台机器发出，就在哪台机器配。

### 方案二：隧道多流并发 ⭐⭐（需改代码）

**收益**: 在 BBR 基础上再叠加（BBR+4 流达 5.3 MB/s，接近链路上限）。

**做法**: tunnel client 对单个大请求拆分成多个 mux 子流并行传输（类似多线程下载器），接收端重组。当前 mux 已支持多子流，需在应用层增加"分片并发下载"逻辑。

**注意**: 与方案一叠加收益递减，BBR 单流已能到 1.6 MB/s，多流主要在更高带宽链路上有意义。

### 方案三：修复隧道停等机制 ⭐⭐（需改底层）

**收益**: 让隧道效率从瓶颈带宽的 30% 提升到接近 90%。

**做法**: P2P 连接层引入**滑动窗口/流水线**（允许多帧在途，窗口 ≥ 带宽×RTT），消除逐帧同步确认。详见 `DEPLOY_TEST_REPORT.md §10.7`。

**与 BBR 的关系**: BBR 解决"链路单流被压制"，滑动窗口解决"隧道协议层逐帧等待"。两者是不同层的问题，需都修才能让隧道带宽真正逼近 1.6 MB/s。

### 方案四：换优质线路（成本方案）⭐

若预算允许，换 **CN2 GIA / 三网优化** 的香港线路，针对大陆访问优化路由，单流原生就快，可减少对 BBR/多流的依赖。

## 4. 推荐实施路径

```
第一步（已完成）: 38 + 所有 relay/server 机器启用 BBR
                  → 单流立即提升 ~27 倍
                  ↓
第二步: 修复隧道停等机制（滑动窗口）
                  → 让隧道带宽逼近 BBR 链路速度 1.6 MB/s
                  ↓
第三步（可选）: 隧道层加多流并发
                  → 进一步榨取到 5 MB/s 级别
                  ↓
第四步（可选）: 换 CN2 GIA 线路
                  → 从物理链路层面再提升
```

## 6. 复现方法

```bash
# 启动测试服务器（38）
ssh relay-host 'nohup /tmp/httpfileserver -bind 0.0.0.0 -port 18080 -size 20 >/tmp/h.log 2>&1 & sleep 7'

# 对比 CUBIC vs BBR 单流
ssh relay-host 'sysctl -w net.ipv4.tcp_congestion_control=cubic'
curl -m 60 -o /dev/null -w "CUBIC: %{speed_download}字节/s\n" http://38.0.0.2:18080/file

ssh relay-host 'modprobe tcp_bbr; sysctl -w net.core.default_qdisc=fq; sysctl -w net.ipv4.tcp_congestion_control=bbr'
curl -m 60 -o /dev/null -w "BBR: %{speed_download}字节/s\n" http://38.0.0.2:18080/file

# 多流测试
for i in $(seq 1 8); do curl -s -m 16 -o /tmp/p$i http://38.0.0.2:18080/file & done; sleep 15
```

## 7. 一句话结论

**本地→香港慢的根因是 CUBIC 在有丢包的跨境链路上误判降速。在 38 服务器启用 BBR 后单流带宽提升 27 倍（0.062→1.672 MB/s），这是零成本立即见效的优化，已实施并持久化。** 隧道要完全发挥这个速度，还需修复协议层的停等机制（滑动窗口）。
