## Full-suite run: 2026-07-13

Command:

```bash

```

| Scenario | Result | Elapsed |
|---|---|---:|
| 01 partition bridges | PASS | 32s |
| 02 Relay failover | PASS | 68s |
| 03 KCP to TCP | PASS | 37s |

Scenario 02 stopped Relay01 during a rate-limited transfer. Relay candidates retained their quality order even when Relay02 was temporarily unreachable during Bootstrap. TCP failures advanced the shared NAT candidate generation after five attempts; KCP failures did not mark a TCP-reachable Relay dead. Registration and business legs observed the same generation, discarded old KCP/TCP legs, and rebuilt on Relay02 with the original `ConnectionId`. Resume legs suppressed the duplicate public-key hello, while all eight in-flight mux sends were woken and retransmitted. The original download completed with curl code `0` and exactly `52,428,800B`.

There was a short convergence window after Relay02 became active: the client business leg reached Relay02 before the server registration was visible, so Relay02 logged `没有 relay 托管目标 nat 节点` for the early resume attempts. The persistent established-stream retry then succeeded as soon as the server registered; this did not duplicate the TLS hello, change the `ConnectionId`, or interrupt the final transfer. This is expected retry noise, but remains a useful latency signal for future registration-first failover optimization.

Scenario 03 observed `11,723` outbound UDP packets before fault injection. TCP then completed the `5,242,880B` transfer with matching hashes, confirming that UDP-only failure remains a protocol fallback rather than a Relay failover trigger.

The post-fix regression suite also verifies the connection lifecycle boundary. A `DualStream` may transparently survive loss of all physical legs only after registration or end-to-end TLS succeeds. Before that point, Relay admission rejection closes the logical stream and the caller's context bounds every TLS send/read, preventing an unavailable or explicitly rejecting Relay from creating an infinite reconnect loop.

`go test ./networkFrameWork -count=1 -timeout=240s` also passed in `144.64s`, including both KCP-blocked and KCP-disconnected stability cases.
