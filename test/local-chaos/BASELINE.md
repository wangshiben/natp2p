# Local chaos baseline

The authoritative baseline is generated by the default command:

```bash
bash scripts/local-deploy-test.sh
```

The default command must run all mandatory scenarios:

| Scenario | Baseline | Meaning |
|---|---|---|
| 01 partition bridges | PASS | Docker isolation, same-Relay routing and the single bridge-Relay path behave as designed. |
| 02 Relay failover | PASS | Both NAT nodes leave a failed entry Relay, register with the replacement Relay, and finish the original transfer. |
| 03 KCP to TCP | PASS | KCP carries data before its path is blackholed; TCP completes the same hash-verified transfer. |

## Expected behavior

Scenario 02 stops the active entry Relay during a rate-limited transfer. TCP
failures advance the shared NAT candidate generation after the configured retry
limit, while a KCP-only failure does not mark a TCP-reachable Relay dead.
Registration and business legs observe the same generation, retire stale
KCP/TCP legs, and rebuild on the replacement Relay with the original logical
connection identity. Resume legs suppress duplicate identity handshakes and
wake in-flight mux sends for retransmission.

A short convergence window is permitted while the replacement Relay waits for
the Server registration. Persistent established-stream recovery must complete
after registration appears without duplicating the first handshake, changing
the logical connection identity, or interrupting the final transfer.

Scenario 03 verifies that a UDP-only failure remains a protocol fallback rather
than a Relay failover trigger. The transfer must have used KCP before fault
injection and must finish over TCP with matching content hashes.

The regression suite also verifies the connection lifecycle boundary. A
`DualStream` may transparently survive loss of all physical legs only after
registration or end-to-end security setup succeeds. Before that point, Relay
admission rejection closes the logical stream and caller contexts bound every
send/read.

## Focused regression commands

```bash
go test ./p2pnode/impl/relaynode -run '^TestBusinessConnect_SchemeB_ClientCannotServe_E2E$' -count=1 -timeout=30s
go test -race ./p2pnode/impl/natnode -run 'TestRelayFailover|TestRelaySelector' -count=1
go test -race ./networkFrameWork -run 'TestLegAvailable|TestResumeLeg|TestReconnectSurvival|Test.*Reconnect' -count=1
```

Host capacity, container resource samples, runtime identifiers, exact timestamps,
and raw network counters are intentionally excluded from this tracked baseline.
Generated evidence remains under ignored local runtime directories.

## Historical failure boundary

Before the failover fixes, scenario 02 kept retrying the dead Relay address and
did not register with the replacement Relay within the gate timeout. The
in-flight download therefore ended without a completion code. The current
baseline requires shared candidate-generation advancement, stale-leg retirement,
registration-first convergence, and successful completion of that original
transfer.
